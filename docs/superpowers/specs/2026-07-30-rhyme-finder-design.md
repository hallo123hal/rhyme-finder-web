# Rhyme Finder Web — Design Spec

Date: 2026-07-30

## 1. Background

`find-rhymes-main` (existing repo) is a Flask app for finding Vietnamese rhymes ("tìm vần") for
rap/lyric writing. Investigation found:

- The core matching function (`giong_am()` in `mainsearch.py`) compares a dictionary word against
  `str(list)` of a signature — a bug that means it never actually matches, so the deployed rhyme
  search silently returns nothing.
- `app/__init__.py` mixes in an unrelated face-mask-detection project (imports `cv2`, `torch`,
  `openai`, `pymongo`, `mysql.connector`), making the codebase fragile to run and unrelated to the
  rhyme feature.
- The one valuable asset is `app/rhymes/data/200k.txt`: ~200k Vietnamese words/phrases.

Decision (confirmed with user): rebuild from scratch rather than patch the old repo. Reuse the
`200k.txt` word list as the starting dataset.

Stack decision: Next.js (TypeScript), deployed on Vercel, instead of Flask/Python, because:
- The rhyme logic is pure string/dictionary processing — no ML or scientific-Python dependency
  needed — so porting to TypeScript costs nothing in capability.
- Vercel hosting for Next.js is push-to-deploy with a free tier; Flask would need a persistent
  server (Render/Railway/VPS) to host equivalently.
- Data collection/expansion (crawling, cleaning) remains a separate, offline concern and can still
  use Python — it is decoupled from what serves the website (see §8).

## 2. Goals

- Support 5 rhyme-search modes for Vietnamese text:
  - **Vần đơn**: rhyme match on the last 1 syllable.
  - **Vần đôi**: rhyme match on the last 2 syllables.
  - **Vần 3**: rhyme match on the last 3 syllables.
  - **Vần 4**: rhyme match on the last 4 syllables.
  - **Vần đảo** (nói lái): given the last 2 syllables of the input, generate valid reversed/swapped
    pairs (e.g. "phải chăng" → "chẳng phai", "di dời" → "rơi gì").
- Instant, no-reload search UI (type → results update).
- Deployable on Vercel with no database and no server management.
- Architecture that allows the word list to grow later without changing how the site is served.

## 3. Non-goals

- Not fixing or redeploying the old `find-rhymes-main` app.
- Not building an admin UI for managing the dictionary.
- Not implementing a live/queryable database in this iteration (see §8 for the offline-file
  approach actually used).
- Not perfect linguistic coverage of every archaic/loanword spelling — common modern Vietnamese
  syllables are the target.
- Vần đảo ranks candidates by phonetic/dictionary heuristics only (see §7.2) — no semantic/LLM
  judgment of which candidate "sounds best." The user picks from a ranked list.

## 5. Input normalization

Before analysis, input phrases are: trimmed, lowercased, collapsed to single spaces between
syllables, and stripped of punctuation/digits (characters that aren't a Vietnamese letter or
space are removed). This happens once in the API route before calling `analyzePhrase`, so
`lib/phonetics.ts` and `lib/rhymeEngine.ts` can assume clean input.

## 6. Phonetics module (`lib/phonetics.ts`)

Every Vietnamese syllable is decomposed into three parts:

- **Onset** (phụ âm đầu): matched against an ordered table, longest prefix first:
  `ngh` → `ng, nh, th, ph, ch, tr, kh, gh, gi, qu` → single letters
  `b,c,d,đ,g,h,k,l,m,n,p,q,r,s,t,v,x`.
  If stripping the matched onset would leave an empty remainder, the onset is treated as absent
  (whole syllable becomes the rhyme) — avoids producing an empty rhyme for edge cases.
- **Rhyme without tone** (vần không dấu): the remainder after the onset, with the tone mark
  removed from its vowel but the base vowel letter preserved exactly (ơ/ô/ư/ê/ă/â are never
  collapsed to a/o/u/e like the old code did).
- **Tone** (thanh điệu): one of `ngang, huyền, sắc, hỏi, ngã, nặng`, extracted via a full table of
  the 12 Vietnamese vowel letters × 6 tone marks (72 entries). Vietnamese text carries the tone
  mark on exactly one vowel character in the syllable; that character is looked up in the table to
  yield `(base_vowel, tone)`.

```ts
type Tone = 'ngang' | 'huyen' | 'sac' | 'hoi' | 'nga' | 'nang';
interface SyllableAnalysis { onset: string; rhyme: string; tone: Tone; original: string }
function analyzeSyllable(syllable: string): SyllableAnalysis
function analyzePhrase(phrase: string): SyllableAnalysis[]  // split on whitespace
```

Tone groups used for ranking: **bằng** = `{ngang, huyen}`, **trắc** = `{sac, hoi, nga, nang}`.

## 7. Rhyme engine (`lib/rhymeEngine.ts`, `lib/dictionary.ts`)

### 7.1 Vần đơn / đôi / 3 / 4

At module load, `dictionary.ts` reads `data/words.json` (array of lowercase words/phrases),
analyzes each into per-syllable `SyllableAnalysis[]`, and builds four indices (k = 1..4):

```
indexK: Map<string, string[]>   // key = JSON-stringified rhyme array of the last k syllables
                                 // value = phrases with >= k syllables whose last k rhymes match
```

Search for mode k given input phrase:

1. Analyze the input; if it has fewer than k syllables, return an error ("cần ít nhất k âm tiết").
2. Take the last k syllables' rhymes, build the same key, look up `indexK`.
3. Drop any candidate equal to the input itself (case-insensitive).
4. Score each candidate: for each of the k matched positions, `+2` if the tone matches exactly,
   `+1` if it's only in the same tone group (bằng/trắc), `+0` otherwise. Sum = score.
5. Sort by score descending, then alphabetically; return top 200 plus total match count.

Note: candidates are **not** required to have the same total syllable count as the input — only
the trailing k syllables must rhyme. This matches how multi-syllable rhyme schemes are actually
used in rap/lyrics.

### 7.2 Vần đảo (nói lái)

Operates on the last 2 syllables of the input; any earlier syllables are kept as a fixed prefix
and re-attached to every output candidate unchanged.

Given syllables `S1 = (C1, R1, T1)` and `S2 = (C2, R2, T2)` (onset, rhyme, tone):

- Target for new position 1: rhyme `R2`, tone `T1`.
- Target for new position 2: rhyme `R1`, tone `T2`.

Rather than reconstructing spelling (tone-mark placement on diphthongs is ambiguous — e.g. the
"hoà" vs "hòa" debate), `dictionary.ts` precomputes a lookup grouping every real syllable seen
anywhere in `words.json` by its own `(rhyme, tone)` pair:

```
syllablesByRhymeTone: Map<string /* rhyme|tone */, { onset: string; syllable: string }[]>
```

So finding valid completions for a target `(rhyme, tone)` is a direct lookup — no spelling
reconstruction or placement-rule guessing needed.

1. `candidatesPos1 = syllablesByRhymeTone.get(R2 + '|' + T1)`
2. `candidatesPos2 = syllablesByRhymeTone.get(R1 + '|' + T2)`
3. Cartesian product of the two lists = candidate pairs.
4. For each pair, compute two flags:
   - `keepsOriginalOnsets`: pos1's onset equals `C2` and pos2's onset equals `C1`.
   - `isAttestedPhrase`: the two syllables written together also occur as an adjacent pair
     somewhere in the dictionary (precomputed `Set<string>` of all adjacent-syllable bigrams from
     every phrase in `words.json`).
5. Sort: `isAttestedPhrase` first, then `keepsOriginalOnsets`, then alphabetically. Return top 100
   plus total count. The UI marks attested-phrase results distinctly so the user can quickly spot
   the most natural-sounding candidate.

Validation: unit tests assert that `generateDao("phải chăng")` includes `"chẳng phai"` and
`generateDao("di dời")` includes `"rơi gì"`, using a small fixture vocabulary containing those
syllables (not the full 200k dataset, for fast/deterministic tests).

## 8. Data pipeline (offline, not deployed)

`data-pipeline/` is a plain Python folder, run manually/locally, never deployed:

- `convert_200k.py`: one-time script that reads the old repo's `200k.txt`, trims/dedupes/drops
  blank lines, lowercases, and writes `rhyme-finder-web/data/words.json` as a JSON array of
  strings.
- Future word-list growth (crawling more sources, cleaning with pandas, etc.) is out of scope for
  this iteration, but the pipeline directory is where that work would live. The contract with the
  web app never changes: produce a JSON array of words/phrases at `data/words.json`, commit it,
  push — Vercel redeploys automatically. No database, no live-update mechanism in this iteration.

## 9. API

`GET /api/search?word=<phrase>&mode=don|doi|ba|bon|dao`

Response (200):
```json
{ "mode": "doi", "query": "yêu thương", "total": 42, "results": ["...", "..."] }
```
For `mode=dao`, each result item also carries its `attested` and `keepsOriginalOnsets` flags:
```json
{ "mode": "dao", "query": "phải chăng", "total": 3,
  "results": [{ "text": "chẳng phai", "attested": false, "keepsOriginalOnsets": true }, ...] }
```
Error (400) when input has fewer syllables than the mode requires: `{ "error": "..." }`.

## 10. Frontend (`app/page.tsx`)

- Single page: text input + 5 mode tabs (Vần đơn / Vần đôi / Vần 3 / Vần 4 / Vần đảo).
- Debounced (~300ms) fetch to `/api/search` on input change or tab change.
- States: loading, empty-input, no-results ("Không tìm thấy"), too-few-syllables error, results
  list (with attested/keeps-original badges for vần đảo mode).
- New, clean visual design — not reusing the old portfolio-template Bootstrap styling.

## 11. Testing

- `lib/phonetics.test.ts`: `analyzeSyllable` against a representative fixture set covering all 6
  tones, onset edge cases (`gi`, `qu`, `ngh`, no-onset), and the ơ/ô/ư/ê/ă/â distinctions the old
  code lost.
- `lib/rhymeEngine.test.ts`: vần đơn/đôi/3/4 against a small fixture dictionary; vần đảo against
  the two worked examples from this spec (`phải chăng`, `di dời`).
- Framework: Vitest.
